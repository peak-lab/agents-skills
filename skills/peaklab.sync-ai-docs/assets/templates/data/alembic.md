# Alembic Rules

Scope: `**/alembic/**`, `**/migrations/**`

## Review generated migrations

When an ORM model changes, determine whether the project uses Alembic and whether the change needs a migration. Generate a candidate with the project's configured Alembic command, then review it before applying it.

Autogeneration is not a complete schema-diff engine. Check especially for:

- table and column renames represented as drop/add operations;
- destructive drops or narrowing type changes;
- new non-null columns on populated tables;
- server defaults, constraints, indexes, and dialect-specific types;
- objects outside the metadata that Alembic may consider removable.

Never apply an autogenerated migration merely because generation succeeded.

## Preserve migration history

Do not edit a revision that may already have run in a shared environment. Create a follow-up revision unless the project explicitly permits rewriting unpublished history and its deployment state has been confirmed.

Use a descriptive revision message and keep the revision graph valid. Resolve multiple heads intentionally rather than guessing an ancestor.

## Plan reversibility

Implement and test `downgrade()` when the project requires rollback and the operation is safely reversible. If rollback would destroy data or cannot be made reliable, make that limitation explicit and document the recovery path instead of supplying a misleading downgrade.

## Validate safely

Before deployment:

1. inspect the Python operations and rendered SQL for the target dialect;
2. run the upgrade against a disposable or representative database;
3. test downgrade and re-upgrade when rollback is supported;
4. verify application compatibility during staged or rolling deployments.
